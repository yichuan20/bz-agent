# 05 — Integrations

BoltzAgent sits inside the Boltzbit platform. The agent can build and deploy full
apps by calling four cloud services, and users can reach the agent over WhatsApp.
This doc covers those integrations and the remote-workspace deployment model.

## The Boltzbit cloud services

| Service | What it is | Base URL | Agent CLI |
|---|---|---|---|
| **BoltzHub** | App store / creator platform: publish, version, and deploy apps | `boltzhub.com/bz-appstore-api` | `bzapp-template.py` + server `/boltzhub/*` |
| **Dynas** | Database-as-a-service: per-app SQL tables via REST | `flow.boltzbit.com/bz-dynas/api` | `bzapp-dynas.py` |
| **Anksy** | Dynamic API gateway: register routes that mock or proxy | `boltzhub.com/bz-anksy` | `bzapp-anksy.py` |
| **dpyes** | Remote Python execution: snippets + async jobs | `flow.boltzbit.com/bz-dpyes/api` | `bzapp-dpyes.py` |

Together they let the agent scaffold a complete app: **frontend** from a BoltzHub
template, **data** in Dynas, **custom API routes** in Anksy, **server-side
Python** in dpyes, then **push/deploy** via BoltzHub.

### BoltzHub (`server.py` §13, `app.py` `/boltzhub/*`)

- Constants: `BOLTZHUB_API = https://boltzhub.com/bz-appstore-api`,
  `BOLTZHUB_AUTH = https://boltzhub.com` (`server.py:769`).
- Auth: `_boltzhub_token()` prefers a non-expiring `BZ_API_KEY` over the OAuth
  JWT in `$BZ_HOME/credentials.json`; `_credentials_valid()` checks
  token/refresh/expiry.
- Routes: `/boltzhub/check`, `/create-app`, `/push` (an **SSE-streamed**
  build → zip → upload → deploy → poll-status pipeline hitting
  `/v1/creator/apps/{id}/code|deploy|status`), `/apps`, `/versions`,
  `/token-usage`, `/sync`, `/create-version`, `/publish`.
- Startup also polls `/v1/bzcode/latest` to surface bzcode upgrade availability
  (⚠️ this call uses `ssl=False`).
- The template store is documented in
  [`app-templates-api.yaml`](../app-templates-api.yaml): a **template** = code
  archive + metadata; consumers search-and-download the best match (falling back
  to a default). `bzapp-template.py fix-env` cleans a downloaded template's env
  (clears `VITE_OAUTH_CLIENT_ID`/`VITE_DYNAS_APP_ID`, sets the auth gateway).

### Dynas (DB-as-a-service)

A hosted "Dynamic App Service" giving each **app** a set of **tables** with
**columns** and **records**, over REST (auth via `X-API-Key` or JWT). See
[`repo_sys_no_public/web_app_dynas_guidline.md`](../repo_sys_no_public/web_app_dynas_guidline.md)
for the full design philosophy.

- **Schema concept** ([`dynas-schema/products.json`](../dynas-schema/products.json)):
  a table = `name`, `displayName`, `description`, `columns[]`, `relations`,
  `rlsEnabled`. Columns have `type` (integer/text/float/boolean/json/datetime)
  and flags (`unique`, `autoGenerated`, …); `id` is auto-generated. The
  `dynas-schema/` subfolders (`ai_coworker`, `management_tool`,
  `productivity_tool`, `web_platform`) are schema sets for different app
  archetypes.
- **Design guidance** (v1.0, for read-heavy content apps): one primary
  "resources" table + slug-keyed taxonomy tables; **denormalize** for read perf;
  **JSON columns** for tags/stats/nested metadata; media as URLs not BLOBs;
  user-interaction tables separate with RLS only there. Supports filter/sort/
  limit, raw SQL (`/tables/query`), joins, aggregations.
- **Used by**: the agent via `bzapp-dynas.py` (create-app/table, patch-table,
  seed, query, sql), the frontend `files.tsx` via `dynasClient`, and standalone
  dev scripts in `scripts/` (`create-dynas-table.py`, `populate-products.py`,
  `patch-dynas-table.py`, `example-table-operations.py`).
  ⚠️ **Those three `scripts/*.py` hardcode a live-looking API key** — see
  [07 — Tech Debt](./07-tech-debt.md).

### Anksy (dynamic API gateway)

Register HTTP routes at runtime that either **mock** a static response or
**proxy** to a backend. Commands (`bzapp-anksy.py`): `register-route`,
`update/delete/get/list-route(s)`, `import-spec` (bulk from OpenAPI),
`list-apps`. A namespace is auto-created on first route; all paths must start
`/api/`; emits a Swagger UI URL. OpenAPI in
[`bz-anksy-openapi.json`](../bz-anksy-openapi.json).

### dpyes (remote Python)

Register Python **snippets** with input/output JSON schemas; run them
synchronously (`run-snippet`) or submit async **jobs** (`submit-job` /
`job-status`). Commands (`bzapp-dpyes.py`): `create/run-snippet`, `submit-job`,
`job-status`, `list-snippets`.

## WhatsApp (Twilio) — `server.py` §14, `app.py` `/whatsapp/*`

Lets a user chat with the bzcode agent over WhatsApp.

- Config via env: `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM`
  (e.g. sandbox `whatsapp:+14155238886`). Twilio's webhook points at
  `/whatsapp/incoming`.
- **One persistent bzcode process per phone number** (`_whatsapp_sessions` guarded
  by `_whatsapp_lock`); `_WASess` wraps a long-lived agent in `<cwd>/whatsapp/`.
  Session id is derived from `md5(phone)`.
- `POST /whatsapp/incoming` parses the Twilio form (`From`/`Body`), routes to the
  per-number session, and replies via `_send_whatsapp` → Twilio REST (truncated
  to ~1500 chars). `POST /whatsapp/status` logs delivery callbacks.
- [`test_whatsapp.sh`](../test_whatsapp.sh) simulates a Twilio webhook with
  `curl` — no real phone needed.
- ⚠️ The root `whatsapp/` directory is an **empty leftover**; the real one is
  created at runtime under the agent's cwd.

## Deployment model: the workspace reverse proxy

For hosted/remote use, each user gets an isolated container reached via a
subdomain. From [`workspace-reverse-proxy.md`](../workspace-reverse-proxy.md):

```
*.workspaces.boltzhub.com
   → FlowInfra Echo proxy (:8081)  — validates JWT, subdomain → workspace id + port
   → GCE VM Incus proxy device
   → container "workspace-backend" (:18789)  — this bz-agent server
```

An `X-Target-Port` header lets the proxy reach arbitrary in-container ports
(e.g. a Coder-mode preview server) instead of the API.

### Two-layer auth (remote)

From [`mobile-api-reference.md`](../mobile-api-reference.md): mobile/third-party
clients use the **same** endpoints as the web app. Auth is two layers:

1. **Gateway auth** — a BoltzHub JWT (`Authorization: Bearer`) required on every
   request to the remote workspace URL (missing → 401, no workspace → 404).
2. **Agent auth** — `POST /auth` once to give bzcode its AI-API token.

⚠️ **The bz-agent server itself performs no per-request token check** and sets
CORS `*`. On `localhost:18789` there is no gateway at all — the gateway is the
*only* access control, and only in the remote deployment. Do not expose the
server's port directly to the internet.
